# Personal Dashboard Server

## 1. Initial Technical Specification and project purpose

Small, reliable, privacy-conscious personal data server in Python with data displayed on always-on dashboard.

The initial purpose is to receive health data from an iPhone via Apple Health + Apple Shortcuts, store normalized data in a local SQLite database, and expose a local web dashboard showing:

* daily step counts
* workout counts
* selected workout types
* historical summaries
* current-year step progress

The system must be designed so that additional data sources, additional people, additional data types, and additional display devices can be added later without redesigning the core architecture.

The intended deployment is a Raspberry Pi 4 or similar always-on local server.

The initial display device is a Lenovo YT3-X50F. The intended primary display is a TRMNL X e-ink display.

---

## 2. Core architectural principles

The following principles are mandatory.

### 2.1 Data source independence

Apple Health is only one data source.

Do not make Apple Health-specific assumptions throughout the application.

Apple Health data must enter through an ingestion layer and then be converted into the application's internal data model.

Future sources may include:

* another person's Apple Health
* weather
* public transport
* Home Assistant
* other APIs
* manually supplied data

Adding a new source should not require rewriting the dashboard or database architecture.

---

### 2.2 Presentation independence

The database and business logic must not depend on a particular display.

The same backend must eventually be able to serve:

* Lenovo Android tablet
* TRMNL X
* desktop browser
* mobile browser
* future displays

The display should consume an HTTP endpoint or webpage.

The display must not need to understand Apple Health-specific data.

---

### 2.3 Local-first architecture

The database and dashboard are local services.

The database must never be directly exposed to the Internet.

The dashboard should be accessible only from the local network.

Only the health-data ingestion endpoint may eventually need secure remote access so that an iPhone can upload data while away from home.

---

### 2.4 Idempotent ingestion

Repeated uploads must not create duplicate data.

The iPhone may upload overlapping periods deliberately.

The server must safely accept the same data more than once.

Use database uniqueness constraints and UPSERT semantics where appropriate.

Example: Uploading steps for `2026-10-03` twice must result in one logical daily-step record, not double records.

---

### 2.5 Server-side business logic

Calculations and aggregation belong on the server.

The dashboard should primarily render data supplied by the backend.

Do not put important business logic only in frontend.

For example, the server should calculate:
* yearly workout totals
* yearly step totals
* past X time daily steps
* date ranges
* workout-type filtering

The frontend should not independently reproduce those calculations.

## 7. Database design

Use SQLite.

The database file must live outside the source-code directory, for example:

```text
data/dashboard.db
```

The database path must be configurable through an environment variable.

Example:

```text
DATABASE_URL=sqlite:///./data/dashboard.db
```

---

### 7.1. Person table

Create a `people` table.

Suggested fields:

```text
id
name
external_identifier
created_at
updated_at
```

Requirements:

* `id` is generated by the server/database.
* `name` is human-readable.
* `external_identifier` identifies a person to ingestion sources.
* Do not use Apple's identifiers directly as the primary database ID.

Example:

```text
id = 1
name = "Me"
external_identifier = "me"
```

Future example:

```text
id = 2
name = "Spouse"
external_identifier = "spouse"
```

---

### 7.2. Daily steps table

Create:

```text
daily_steps
```

Fields:

```text
id
person_id
date
steps
created_at
updated_at
```

Requirements:

* `date` represents the local calendar date associated with the data.
* `steps` is a non-negative integer.
* `person_id` references `people`.
* `(person_id, date)` must be UNIQUE.

This allows an incoming upload to update an existing day's value.

Do not sum multiple uploads together. If a later upload says:

```text
2026-10-03 = 12500
```

replace/update the existing value.

---

### 7.3. Workout table

Create:

```text
workouts
```

Suggested fields:

```text
id
person_id
date
workout_type
indoor
active_energy_burned
basal_energy_burned
source_id
workout_uuid
created_at
updated_at
```

Requirements:

`workout_type` in initial phase can be a value derived from Apple Health.

`indoor` flag represents indoor/outdoor workouts and defaults to False.

`active_energy_burned` and `basal_energy_burned` are optional, if not present those values defaults to 0.

Apple Health source provides a unique workout identifier, preserve it as `workout_uuid`.

Create a uniqueness constraint such as:

```text
(person_id, workout_uuid)
```

This prevents duplicate workout records when the same Apple Health data is uploaded repeatedly.

---

### 7.4. Data source table

Create:

```text
data_sources
```

Example values:

```text
apple_health
home_assistant
weather
manual
```

Fields:

```text
id
name
type
created_at
```

This allows additional sources to be introduced later.

---

### 7.5. Ingestion event table

Create:

```text
ingestion_events
```

This is primarily for operational visibility and might be implemented at later phase.

Suggested fields:

```text
id
source_id
person_id
received_at
status
records_received
records_created
records_updated
error_message
request_id
```

Do not store the complete health payload by default.

Health data is sensitive.

The ingestion log should contain metadata necessary to determine whether ingestion succeeded without unnecessarily retaining the original payload.

## 8. Apple Health ingestion

The application must expose:

```text
POST /api/v1/health
POST /api/v1/workouts
```

These endpoints accept JSON generated by Apple Shortcuts.

Do not assume that Apple Health's raw export format is the application's internal database format.

Create a dedicated parser/adapter:

```text
Apple Health JSON
       ↓
AppleHealthParser
       ↓
normalized internal records
       ↓
database
```

This keeps Apple-specific logic isolated.

---

## 9. Normalized ingestion model

The ingestion service should internally convert input into something conceptually equivalent to:

```python
{
  "2026-09-28": 10123,
  "2026-09-29": 9854,
  ...
}
```
for POST /api/v1/health, and:
```python
{
  "workout_uuid_1": {
      "date": "2026-09-28",
      "workout_type": "traditionalStrengthTraining",
      "indoor": True,
      "active_energy_burned": 284,
      "basal_energy_burned": 0,
      "source_name": "Strong",
      "workout_uuid": "workout_uuid_1",
    },
  "workout_uuid_2": {
      "date": "2026-09-30",
      "workout_type": "walking",
      "indoor": False,
      "active_energy_burned": 401,
      "basal_energy_burned": 165,
      "source_name": "Apple Watch",
      "workout_uuid": "workout_uuid_2",
    },
    ...
}
```

The exact Apple Shortcut payload can be different.

The important requirement is that the ingestion service produces this normalized representation.

## 10. Upload a range, not only one day

The Shortcut should preferably upload the last several days of data rather than only today's data.

Recommended initial strategy:

```text
Every day:
upload the previous 7 days
```

The server performs UPSERT operations.

This makes the system resilient to:

* temporary network failures
* missed Shortcut executions
* corrections to Apple Health data
* duplicate uploads
* late-arriving data

Example:

```text
October 4 uploads period: September 28 → October 4
October 5 uploads period: September 29 → October 5
```
Overlapping data must be safe.

---

## 11. Ingestion authentication

The health ingestion endpoint must require authentication.  

Do not expose an unauthenticated health-data POST endpoint.

Initial phase authentication can use a strong random bearer token. 

Example:

```text
Authorization: Bearer <INGESTION_TOKEN>
```

The token must be stored as a server-side secret/environment variable.

Do not hard-code the token in source code. Do not commit secrets to Git.

Separate tokens per person must be supported. The token should identify which ingestion person is authorized.

---

## 12. Remote ingestion architecture

The dashboard itself should remain LAN-only.

However, the health ingestion endpoint may eventually need to be reachable from outside the home network.

Preferred architecture:

```text
iPhone
   |
   | HTTPS
   |
   v
secure remote entry point
   |
   v
POST /api/v1/health
POST /api/v1/workouts
   |
   v
local server
```

Do NOT expose the SQLite database.

Do NOT expose SSH.

Do NOT expose the complete FastAPI application unnecessarily.

Do NOT open arbitrary router ports.

The remote exposure mechanism is intentionally outside initial hase.

Initial phase should first work locally.

## 19. Security requirements

### Must

* Never expose SQLite directly.
* Never expose database credentials because SQLite has none; protect the database file through OS permissions.
* Require authentication for health ingestion.
* Never hard-code secrets.
* Never commit `.env` files.
* Validate all incoming JSON.
* Reject malformed input.
* Limit request body size.
* Log ingestion metadata, but avoid logging sensitive payloads.
* Do not return internal exceptions to clients.
* Keep dashboard LAN-only initially.

### Should

* Use HTTPS for remote ingestion.
* Use a reverse proxy/tunnel for future remote access rather than router port forwarding.
* Use separate ingestion tokens per person.
* Rotate tokens when necessary.
* Rate-limit the public ingestion endpoint.

---

## 20. Privacy requirements

Health information is sensitive.

Therefore:

* Store only required information.
* Do not permanently store raw Apple Health JSON unless explicitly enabled.
* Do not log complete health payloads.
* Do not expose health records through generic debugging endpoints.
* Do not include personal health information in application logs.
* Keep the database on local storage.
* Keep backups protected.

---

## 21. Error handling

The server must distinguish between:

### Invalid request

Return:

```text
400 / 422
```

as appropriate.

Do not modify the database.

---

### Authentication failure

Return:

```text
401
```

Do not reveal whether the supplied person/source exists.

---

### Valid request but database failure

Return:

```text
500
```

and log the internal error.

Preferably:
Do not partially commit data.
Use transactions so that one ingestion request is atomic where practical.

---

### Duplicate data

Do not return an error merely because data already exists.

Perform an update/no-op according to the ingestion rules.

# 22. Request IDs

Every API request should have a request ID.

If the client does not provide one, the server should generate one.

Use the request ID in logs.

The ingestion response should include the request ID.

Example:

```json
{
  "status": "accepted",
  "request_id": "..."
}
```

This makes debugging Apple Shortcut failures considerably easier.

## 28. Time and timezone rules

Configure `APP_TIMEZONE` with a valid IANA timezone. Use it to determine the local calendar date for dashboard periods and incoming timezone-aware health(step) and workout timestamps.

Convert timezone-aware incoming timestamps to `APP_TIMEZONE` before extracting their calendar date. For timezone-naive timestamps, use the date as supplied; do not infer a timezone.

Store daily health measurements and workout dates as calendar dates. Store application timestamps in UTC.

## 33. Critical architectural rule

The most important rule in this project is:

```text
DATA SOURCE
     ↓
INGESTION / NORMALIZATION
     ↓
DATABASE
     ↓
BUSINESS LOGIC / API
     ↓
PRESENTATION
     ↓
DISPLAY
```

Never couple these layers unnecessarily.

In particular:

```text
Apple Health
```

must not be directly coupled to:

```text
dashboard HTML
```

and:

```text
TRMNL X
```

must not be directly coupled to:

```text
SQLite
```

The database is the persistent source of truth.

The API is the contract between stored data and presentation.

The display is a client.
